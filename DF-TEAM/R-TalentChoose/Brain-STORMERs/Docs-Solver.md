# 🪄 Docs-Solver

### What is a Docs-Solver?

A Docs-Solver is a person and a way to contribute.

Someone who works with knowledge that already exists and notices when it could be clearer, more accurate, better structured or simply easier to use.

Maybe you are the person who always notices the wrong word in a sentence. Maybe you read a technical explanation and think, *“I understand every word, but I still don't know what I'm supposed to do.”*

That can be useful here.

### Work with what already exists

You can correct documentation, rewrite confusing explanations, suggest a new document, reorganize information, simplify a difficult section or point out contradictions.

You can work with current files or historical ones.

The goal is not to make everything simpler at any cost. Technical accuracy still matters.

A good explanation should be understandable without throwing away the details that make it correct.

### You can find the problem without fixing it

You do not need to arrive with a finished replacement.

If something is outdated, contradictory or difficult to understand, point to the exact place and explain what makes it a problem.

Someone else may fix it later.

If you are able to compare the documentation with the current architecture and find the exact mismatch, even better. If you can prepare a Pull Request with the correction, that is another way to leave the problem already partly solved.

But simply noticing something that everyone else missed is already a contribution.

### Look at it from outside

Read the documentation as if you were using DF-SHE for the first time.

What would make you stop?

What would make you misunderstand the architecture?

What would make you search for an answer that should already be here?

Those observations can become useful documentation work.

You are not complaining that *“nothing makes sense.”*

You are showing where the information could work better.

### Technical knowledge is optional

You can contribute through English, grammar, structure, clarity and attention to detail.

Technical experience gives you another useful view: you may notice when documentation does not match the actual code, architecture or behaviour of the project.

Both views matter.

### How to contribute

Find something that could be corrected, clarified or structured better.

Read the surrounding information before changing it.

Keep the original meaning and technical accuracy intact.

Then either propose the correction publicly or make the correction yourself through the appropriate DF-SHE channel.

[See how to create an Issue →](../../Assets/classic-github-docs/github-issue-creating.md)

[See how to create a Pull Request →](../../Assets/classic-github-docs/github-pull-request.md)

A single meaningful sentence can be enough to prevent someone else from misunderstanding an entire part of the project.

### Docs-Solver, Questioner and Idea-creator

Questioner asks: **Why is it like this?**

Idea-creator asks: **What if we changed it?**

Docs-Solver asks: **Is the information here correct, useful and understandable?**

They can meet in the same contribution.

### What makes this role different?

You do not have to create something new.

Sometimes the most useful thing you can do is make sure something that already exists is not misunderstood, lost or left behind.

**Docs-Solver is a contribution method, not a title or profession.**
